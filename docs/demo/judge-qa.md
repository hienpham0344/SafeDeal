# Judge Technical Q&A (SEApp UIT — Bảng App)

**Q1: Can the SafeDeal backend or deployer ever freeze, censor, or sweep locked AVAX?**
No. `SafeDealEscrow.sol` has no owner, admin role, pause toggle, or sweep function. Only `releaseFunds` (buyer), `refundBySeller` (seller), `refundAfterDeadline` (buyer after deadline), `submitResolutionVote` (2-of-3 consensus across `[buyer, seller, arbiter]` enforcing `buyerAmount + sellerAmount == trade.amount`), or `resolveDisputeByTimeout` (deterministic 50/50 split after 14 days) can credit `_claimableBalances`. Recipients call `withdraw()` directly on-chain.

**Q2: What happens if a malicious smart contract acts as buyer/seller and reverts in `receive()` during split arbitration?**
Push transfers would deadlock funds. SafeDeal isolates payouts via **pull-payment withdrawals** (`_claimableBalances` + `withdraw()`). Even if one party's contract deliberately reverts on transfer, dispute settlement completes cleanly and the honest counterparty withdraws their share normally.

**Q3: How do you guarantee off-chain readable deal descriptions match what was signed on-chain?**
Browser (`canonical-terms.ts`), Manifest V3 Chrome Extension (`extension/shared/canonical-terms.js`), and Rust backend (`crates/domain/src/canonical_terms.rs`) all serialize the commercial terms object into identical RFC 8785 Canonical JSON and compute SHA-256 (`termsHash`). `createTrade` commits `termsHash` on-chain, and `BindDealTransactionUseCase` / `SyncDealUseCase` verify equality against on-chain logs and `getTrade` before binding or reconciling deals.

**Q4: Why do you use a dual-mode session strategy (`HttpOnly` cookie + `X-CSRF-Token` paired with `Authorization: Bearer` fallback)?**
Same-site requests use an `HttpOnly` HS256 JWT cookie (`safedeal_session`) paired with `safedeal_csrf` + `X-CSRF-Token` Double-Submit verification in `csrf_protection_middleware`. Because modern browsers (Safari ITP, Chrome third-party cookie restrictions, Brave) often block cross-site cookies between decoupled cloud hosts like Firebase Hosting (`avalanche-9b099.web.app`) and Railway (`safedeal-production.up.railway.app`), SafeDeal also supports an `Authorization: Bearer <token>` header fallback—including authenticated `fetch()` -> `Blob` downloads (`downloadAuthenticatedAttachment`) for private dispute evidence.

**Q5: How do you prevent an RPC outage or spoofed HTTP headers from degrading backend stability or auth security?**
1. `AlloyBlockchainGateway` JSON-RPC calls run explicitly **outside** PostgreSQL transactions (`UnitOfWork::in_tx`) so slow RPC responses never exhaust `sqlx::PgPool` connections.
2. `AuthRateLimitState` keys sliding-window limits on Axum `ConnectInfo<SocketAddr>` peer IP by default (`AUTH_TRUST_PROXY_HEADERS=false`, ignoring untrusted `X-Forwarded-For` headers) with bounded map eviction.

**Q6: What prevents malicious polyglot image uploads, local disk tampering, or non-participants from reading private dispute evidence?**
`LocalEvidenceStorageAdapter` (and `S3EvidenceStorage`) validates declared MIME types (`image/png`, `image/jpeg`, `application/pdf`, `text/plain`), verifies binary **magic-byte signatures**, writes UUID filenames with path-traversal/symlink containment checks, and computes SHA-256 (`sha256_hex`). On download, `DisputeUseCase::prepare_evidence_download` enforces caller participation/arbiter ACL (`403` for non-actors), **re-verifies SHA-256 byte integrity (`evidence.verify_bytes_integrity`) for both local disk and S3 payloads**, and serves bytes with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store`.

**Q7: What if the seller refreshes `/create` mid-transaction or backend `bind-tx` returns `503`?**
`CreateDealPage` persists the drafted preview, `clientTermsHash`, and `submittedCreateTxHash` per seller address in `sessionStorage` alongside pending tx tracking. On reload, it either waits for the existing tx receipt or presents **Retry Backend Binding**, never invoking `createTrade` twice.

**Q8: Game-Theory Question — What if a Seller delivers valid work (`DELIVERED`), the Buyer stays silent after `inspectionWindow`, the Seller opens a dispute (`openDispute`), and both Buyer & Arbiter stay silent for 14 days? Doesn't `resolveDisputeByTimeout` give the malicious silent Buyer a 50/50 split?**
This is an intentional layered liveness vs. fairness design with three concrete defenses:
1. **2-of-3 SLA Arbiter Resolution (Normal Path, 24–48h)**: Once `deliveredAt + inspectionWindow` expires, the Seller calls `openDispute(tradeId)` and uploads delivery proof (signed with SHA-256 & magic-byte validation). Because SafeDeal uses **2-of-3 consensus (`submitResolutionVote`)**, the Seller does **not** need the silent Buyer's signature: the Seller votes `100% Seller / 0% Buyer`, and the designated SLA Arbiter reviews the evidence within 24–48 hours and submits a matching `100% Seller / 0% Buyer` vote. That reaches 2-of-3 consensus (`Seller + Arbiter`) and releases **100% of the funds to the Seller** days before the 14-day clock expires.
2. **Why the 14-Day 50/50 `resolveDisputeByTimeout` Exists (Catastrophic Liveness Fallback)**: The 14-day timeout (`DISPUTE_TIMEOUT = 14 days`) only triggers in the catastrophic double-fault case where **both** the Counterparty AND the designated Arbiter permanently disappear or lose their keys simultaneously. Without an on-chain timeout, `100%` of the Seller's funds would be frozen forever in the smart contract; `resolveDisputeByTimeout` guarantees deterministic capital recovery with zero admin backdoors.
3. **V2 Protocol Roadmap (`claimAfterInspection` + ERC-20 `USDC`/`USDT`)**: For standardized digital deliveries where no arbiter is desired on silent buyers, SafeDeal V2 introduces `claimAfterInspection(tradeId)` (allowing the Seller to claim `100%` directly on-chain if the Buyer neither calls `releaseFunds` nor `openDispute` within `deliveredAt + inspectionWindow`), alongside `SafeERC20` stablecoin vaults (`USDC`/`USDT` on Avalanche C-Chain) to eliminate crypto price volatility during multi-day escrow windows.

**Q9: How does the Manifest V3 Chrome Extension (`extension/`) verify on-chain deals inside social/marketplace workflows without compromising wallet security?**
P2P negotiations happen on Facebook Groups, Messenger, Discord, Telegram, Chợ Tốt, or GitHub—not inside an escrow dashboard. The **`SafeDeal Escrow Companion` (`extension/`, Manifest V3)** embeds verification right where negotiations happen while staying **100% non-custodial**:
1. **Zero-Key, Zero-SIWE Read-Only RPC Verification (`shared/rpc-client.js`)**: When a user pastes a SafeDeal link (`/deals/<tradeId>`) or `tradeId` into the Chrome Side Panel (or hovers a link scanned by `content/deal-verifier.js`), the extension performs a direct read-only JSON-RPC `eth_call` (`getTrade(bytes32)` and `getDisputeVotes(bytes32)`) against Avalanche Fuji (`https://api.avax-test.network/ext/bc/C/rpc`). It verifies on-chain `status` (`FUNDED`, `DELIVERED`, `RELEASED`, `DISPUTED`), locked AVAX amount, counterparty addresses, deadlines, and `termsHash` **without ever touching private keys or requiring a wallet login**.
2. **Local Web Crypto RFC 8785 `termsHash` Checker (`shared/canonical-terms.js`)**: Uses the exact deterministic RFC 8785 canonical JSON algorithm as `frontend/src/utils/canonical-terms.ts` and `backend/crates/domain/src/canonical_terms.rs` via browser `crypto.subtle.digest("SHA-256", ...)` to prove whether off-chain chat terms match the on-chain `bytes32 termsHash`.
3. **Manifest V3 Performance & Security Compliance**: Adheres to all 20 Chrome Extension MV3 engineering rules—ephemeral service worker state persisted in `chrome.storage.local` + `chrome.alarms`, DOM link annotations batched in chunks of 15 via `requestAnimationFrame` + `scheduler.yield()`, isolated closed Shadow DOM toast confirmations, and zero `eval()` or inline scripts.
